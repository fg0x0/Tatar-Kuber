## Two things v1.0.1 did not fix

**1. Kubescape's mapping was still wrong in 6 places.** v1.0.1 shipped the Popeye, Trivy and Checkov
mapping audits, but Kubescape's own audit landed after the tag. It held the second-worst set —
**6 of 28 mappings wrong, including two swapped pairs**:

| Rule | Upstream meaning | Was mapped to |
|---|---|---|
| `C-0187` | Minimize wildcard use in Roles and ClusterRoles | Default service account in use |
| `C-0272` | Workload with administrative roles | Wildcard permissions in role |
| `C-0078` | Images from allowed registry | Critical/High CVE in image *(Kubescape does not scan image CVEs at all)* |
| `C-0075` | imagePullPolicy check | `:latest` tag |
| `C-0018` | readiness probe only | readiness **and** liveness *(liveness is the separate `C-0056`)* |

`C-0187` and `C-0272` were each sitting in the other's place, so on a ClusterRole with wildcard verbs
the two collapsed into one finding instead of reporting RBAC-001 (CRITICAL) and RBAC-002 (HIGH)
separately. Coverage went from 28 rules with 17 unmapped to **35 with only 2 deliberately unmapped**.

**Kubescape's RBAC findings also had empty names.** Subjects of kind `Group`/`User` carry their name
in a top-level `name` field, not `metadata.name` — so those findings came out as `group/` and `user/`
with nothing after the slash, which made the dedup key collide and **merged different subjects into a
single finding**. Names are now resolved (`metadata.name` → `object.name` → resourceID tail), and each
subject's bound role is attached as evidence (`clusterrole/cluster-admin`) — the detail an auditor
actually needs.

**2. Pod ↔ Deployment double counting.** Scanners report the *same* issue at different object levels:
Trivy k8s and Kubescape check the **workload** (`deployment/api`), while Popeye runs its `deployments`
and `pods` linters separately — so one pod-template violation became two findings, and a 5-replica
Deployment reported it five more times. Finding counts and the cluster risk score were inflated
accordingly.

`internal/rollup` now moves pod-scoped findings onto their owning controller **before** dedup, so they
merge normally. It does not guess. Without a cluster connection there are no `ownerReferences` to read,
so a finding is only moved when **all** of these hold:

1. a controller-level finding for the **same canonical control** already exists in that scan (no
   object is ever invented — only an existing one is used),
2. the controller is in the **same namespace**, and
3. the pod's name is the controller's name plus a suffix that matches what Kubernetes actually
   generates.

The discriminator for (3) is that Kubernetes' `rand.SafeEncodeString` uses a **vowel-free** alphabet
(`bcdfghjklmnpqrstvwxz2456789`) precisely so generated names never spell words. So
`api-598c4dc6b8-ldjqq` is a pod of `api`, while `api-canary` is a different workload — not a
"looks like a hash" guess. Longest controller name wins, so `api` never claims
`api-gateway-7d9f8-abcde`.

Nothing is lost: every moved pod is kept in the finding's evidence as `pod/<name>`, the move count and
pod list are published in `metadata.rollup` and printed in the report, and `--no-rollup` turns it off
entirely. Getting a rollup wrong would misattribute a finding to the wrong object — an audit error —
whereas missing one only duplicates a count, which is visible and harmless. So when in doubt, it does
not move.

## Smaller correctness fixes

- **Namespace asset context matched substrings.** `strings.Contains(ns, "prod")` meant
  `non-production` was scored as production (1.3× exposure). Matching is now token-based (splitting on
  `-`, `_`, `.`), and `nonprod` / `preprod` resolve to dev.
- **Blind-shot rules are validated at registry load.** A rule with no selector, an invalid
  `downgrade_to`, or a missing reason is now a hard error instead of a silently dead rule.
- **Never-matched suppressions are reported**, as are policy rules naming a control that does not
  exist — a typo in `.tatar-kuber.yaml` no longer hides silently.
- **SARIF findings that carry a file path now emit a real file:line region**, so GitHub Code Scanning
  annotates the right line instead of the top of the file.
- The `docs/04_Severity-Risk-Scoring-Model.docx` mismatch noted in the v1.0.1 release is fixed: all
  six engineering documents are reconciled with the code (Version 1.2).

## Verification

16 test packages green, `go vet` clean, registry validation passing. Every mapped rule in all four
scanners is pinned by a test against upstream's own definitions. Demo dataset: 75 findings with
`rollup: {moved: 3}`; lab regression baseline: 19 controls / 69 findings, `verify-lab` PASS.

## v1.0.1-д зассангүй хоёр зүйл

**1. Kubescape-ийн зураглал 6 газар буруу хэвээр байсан.** v1.0.1-д Popeye, Trivy, Checkov-ийн
зураглалын аудит орсон боловч Kubescape-ийн аудит tag-ийн дараа дууссан. Тэр нь хоёрдугаарт хамгийн
их зөрүүтэй байлаа — **28 зураглалын 6 нь буруу, түүний дотор хоёр хос сольж бичигдсэн**:

| Rule | Upstream утга | Зурагдсан байсан нь |
|---|---|---|
| `C-0187` | Minimize wildcard use in Roles and ClusterRoles | Default service account in use |
| `C-0272` | Workload with administrative roles | Wildcard permissions in role |
| `C-0078` | Images from allowed registry | Critical/High CVE in image *(Kubescape image CVE-г огт шалгадаггүй)* |
| `C-0075` | imagePullPolicy-ийн шалгалт | `:latest` tag |
| `C-0018` | зөвхөн readiness | readiness **ба** liveness *(liveness нь тусдаа `C-0056`)* |

`C-0187` ба `C-0272` нь тус бүр нөгөөгийнхөө оронд байсан тул wildcard verb-тэй ClusterRole дээр
RBAC-001 (CRITICAL) ба RBAC-002 (HIGH) гэж тусад тайлагнахын оронд хоёр нь нэг finding болж
нийлж байв. Хамрах хүрээ 28 rule/17 зураглалгүйгээс **35/2 (зориудаар)** болов.

**Kubescape-ийн RBAC finding-үүд хоосон нэртэй гарч байсан.** `Group`/`User` төрлийн subject нэрээ
дээд түвшний `name` талбарт өгдөг, `metadata.name`-д БИШ — тиймээс тэдгээр finding нь `group/`,
`user/` гэж зураасны дараа юу ч байхгүй гарч, dedup түлхүүр давхцан **өөр өөр subject нэг finding
болж нийлж байв**. Одоо нэр зөв тодорхойлогдож (`metadata.name` → `object.name` → resourceID-ийн
сүүл), subject бүрийн хамаарах role нь нотолгоонд орж байна (`clusterrole/cluster-admin`) —
аудиторт яг тэр мэдээлэл хэрэгтэй.

**2. Pod ↔ Deployment давхардал.** Scanner-ууд НЭГ асуудлыг өөр өөр объектын хэмжээнд тайлагнадаг:
Trivy k8s ба Kubescape нь **workload**-ыг (`deployment/api`) шалгана, харин Popeye нь `deployments`
ба `pods` linter-ээ тус тусад ажиллуулдаг — тиймээс pod template-ийн нэг зөрчил хоёр finding болж,
5 replica-тай Deployment бол дээр нь бас 5 удаа тайлагнаж байв. Finding-ийн тоо ба cluster-ийн
эрсдэлийн оноо дагаад хөөрөгдөж байсан.

Одоо `internal/rollup` нь pod хэмжээний finding-ийг эзэмшигч controller руу dedup-аас **ӨМНӨ**
зөөх тул тэд хэвийн нэгдэнэ. Таамаглал БИШ. Cluster-т холбогдохгүй тул `ownerReferences`
уншигдахгүй, тиймээс зөвхөн **бүх** нөхцөл хангагдсан үед зөөнө:

1. тухайн scan дотор **ЯГ ТЭР canonical control**-д controller хэмжээний finding аль хэдийн байгаа
   (объектыг хэзээ ч зохиохгүй — байгааг л ашиглана),
2. controller нь pod-той **ижил namespace**-д байгаа,
3. pod-ийн нэр нь controller-ийн нэр дээр Kubernetes-ийн БОДИТООР үүсгэдэг дагавар нэмсэн хэлбэртэй.

(3)-ын гол шалгуур нь Kubernetes-ийн `rand.SafeEncodeString` нь үүсгэсэн нэр санамсаргүй үг болохоос
сэргийлэхийн тулд **эгшиггүй** алфавит (`bcdfghjklmnpqrstvwxz2456789`) хэрэглэдэг гэдэг. Тиймээс
`api-598c4dc6b8-ldjqq` бол `api`-ийн pod, харин `api-canary` бол өөр workload — "хэш шиг харагдаж
байна" гэсэн таамаг биш. Хэд хэдэн тохирвол нэр урт нь дийлдэг тул `api` нь
`api-gateway-7d9f8-abcde`-ийг хэзээ ч эзэмшихгүй.

Юу ч алдагдахгүй: зөөгдсөн pod бүр finding-ийн нотолгоонд `pod/<нэр>` болж хадгалагдана, зөөлтийн тоо
ба pod-ын жагсаалт `metadata.rollup`-д гарч тайланд хэвлэгдэнэ, `--no-rollup`-аар бүрэн болино.
Буруу зөөвөл finding өөр объектод хамааруулагдана — энэ нь аудитын алдаа; зөөхгүй өнгөрвөл зөвхөн
тоо давхардана — энэ нь харагддаг, хор хөнөөлгүй. Тиймээс эргэлзвэл зөөхгүй.
